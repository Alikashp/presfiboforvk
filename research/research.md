## 1. Старый репозиторий: инвентаризация и приговор

Репозиторий `alikashp/fibomy2.0.0` — Telegram-бот, который генерирует
презентации как **HTML → PDF через Playwright** по четырём собственным
Jinja-шаблонам. 4 003 строки Python в 15 модулях.

Ключевой факт: **`.pptx` на выходе не производится вообще**. `python-pptx` в
зависимостях используется только на вход — вытащить текст из загруженного
пользователем файла (`content_extractor.py`). То есть главное требование ТЗ
(нативный экспорт в .pptx) в старом коде не реализовано ни в каком виде.

## 2. Датасет: что на самом деле прислали

Приложены **3 файла `.pptx`, контент-пакета в приложении нет** (см. открытый
вопрос Q3).

### 2.1. Измеренные параметры

| | vk_tech | vk_education | vk_workspace |
|---|---|---|---|
| слайдов | 54 | 55 | 29 |
| размер слайда (EMU) | 9144000×5143500 (10″×5.63″) | 12192000×6858000 (13.33″×7.5″) | 12192000×6858000 |
| мастеров | 2 | 2 | 1 |
| layout'ов | 39 | 30 | 15 |
| media | 222 PNG | 254 PNG + 3 JPG | 32 PNG |
| **нативных графиков (`c:chart`)** | **0** | **0** | **0** |
| нативных таблиц (`a:tbl`) | 0 | 3 | 1 |
| SmartArt (`dgm:`) | 0 | 0 | 0 |
| `grpSp` / `cxnSp` | 6 / 0 | 19 / 41 | 28 / 4 |
| встроенные шрифты | Play regular+bold | Play regular+bold | Play regular+bold |
| вес файла | 20.5 МБ | 23.9 МБ | 13.4 МБ |

Все три — колоды, экспортированные через **Google Slides** (имена фигур вида
`Google Shape;904;p62`). Следствие: **имена фигур семантически пусты**, опираться
на них нельзя — что удобно, потому что и соблазна захардкодить нет.

### 2.2. Находка 1: тема (`theme1.xml`) ≠ дизайн-система

```
vk_tech       clrScheme: accent1=0077FF accent3=FF3885 lt1=FAFCFF   fontScheme: Office / Arial
vk_education  clrScheme: accent1=0077FF accent2=FF3885 accent3=7CEDF8 fontScheme: Office / Arial
vk_workspace  clrScheme: accent1=4472C4 accent2=ED7D31 accent3=A5A5A5 fontScheme: Office / Arial
```

У `vk_workspace` `clrScheme` — **стоковая офисная палитра** (4472C4/ED7D31/…),
которая не имеет отношения к реальному оформлению колоды. Реальные цвета, взятые
подсчётом по XML слайдов: `0077FF` ×153, `000000` ×145, `E4E7EA` ×53, `212121`
×49, `00AEE8` ×45, `6DBCFF` ×24. `fontScheme` у всех трёх — дефолтный `Arial`,
при том что фактически на слайдах доминирует `Play` (vk_tech 746 вхождений,
vk_workspace 360, vk_education 315).

**Вывод, определяющий архитектуру: токены нельзя брать из темы. Их надо
добывать статистикой фактического употребления по слайдам/мастерам/layout'ам,
а тему использовать только как слабый приор и как словарь для резолва
`schemeClr` → RGB.**

### 2.3. Находка 2: layout'ы почти не несут контентных плейсхолдеров

- **vk_workspace**: все 15 layout'ов имеют ровно **один** плейсхолдер (`TITLE`)
  и 3–9 декоративных фигур. Контентных плейсхолдеров — ноль.
- **vk_tech**: 36 из 54 слайдов сидят на layout `1_Свободный дизайн`, у которого
  один `TITLE`. Ещё 14 layout'ов вида `N_Контент` — тоже по одному `TITLE`.
- **vk_education** — единственный с настоящей семантикой в layout'ах
  («Заголовок + текст в две колонки», «2 фактоида + текст», «Цитата без фото»,
  «1 фото + подпись»). Но и там 27 из 55 слайдов стоят на layout `Заголовок`
  с единственным `TITLE`.

**Вывод: стартовая гипотеза «слайд собирается на layout шаблона по его
плейсхолдерам» покрывает меньшинство случаев. Это не запасной путь, а
основной: композицию надо добывать из слайдов-примеров.** Описанный в ТЗ
edge-case («шаблон может быть просто колодой с оформленными слайдами»)
на этом датасете — норма, а не исключение.

### 2.4. Находка 3: все три колоды — библиотеки паттернов с рыбным текстом

Рендер в PNG (LibreOffice → PDF → pdftoppm, 138 страниц, просмотрено глазами)
показал, что это не «примеры презентаций», а **каталоги готовых композиций**,
заполненные заглушками: «Заголовок в две или в одну строчку», «Текст»,
«Описание», «Пункт», «Вставить фото», «Имя Фамилия», «Должность», «>50%»,
«XXX%», «Название команды».

Это лучший возможный вход: 138 размеченных дизайнером композиций с реальной
геометрией, реальными стилями и заглушками, прямо называющими роль слота.

`vk_education` вдобавок — **брендбук**: на слайдах написаны словесные правила
(«Точки используются для навигации. Число разделов = число точек.», «Текст
выравниваем по центру и по середине фигуры», «Иконки можно брать из этого
слайда, масштабировать и изменять цвет»), лежит **библиотека из ~100 иконок**
(слайд 25) и примеры схем и диаграмм.

### 2.5. Находка 4: повторяющиеся группы — это компоненты с сеткой

Разбор vk_tech, слайд 21 (карточная сетка):

```
grpSp #907 (x=0.56″, w=1.77″, h=2.53″)   ┐
grpSp #919 (x=2.91″, w=1.77″, h=2.53″)   │ шаг 2.35″, зазор 0.58″
grpSp #931 (x=5.26″, w=1.77″, h=2.53″)   │ внутренняя структура
grpSp #943 (x=7.63″, w=1.77″, h=2.53″)   ┘ всех четырёх идентична
```

Внутри каждой группы — одинаковый набор: иконка (`pic`) + «Заголовок» +
«Подзаголовок» + 2×«Текст» + 3 буллета с маркерами. То есть паттерн
раскладывается на **item-template + сетку (n, шаг, зазор)** и переинстанцируется
под любое число элементов. Это делает «плотность контента» и «число элементов»
настоящими параметрами вёрстки, а не фантазией.

Техническая деталь: координаты детей группы живут в системе координат группы
(`a:xfrm/a:chOff`,`a:chExt`), python-pptx их не пересчитывает. Абсолютный bbox
надо считать самим — иначе детерминированные проверки «выход за границы» и
«наложение блоков» дадут мусор.

### 2.6. Находка 5: встроенные шрифты — это EOT с MTX-сжатием

`ppt/fonts/Play-regular.fntdata`: первые 4 байта `9e d7 00 00` = 55198 =
ровно размер файла. Это **EOT** (Embedded OpenType), версия `0x00020002`,
флаги `0x4` = `TTEMBED_TTCOMPRESSED`. Сигнатуры `\x00\x01\x00\x00` / `OTTO`
в файле нет — тело сжато MicroType Express, простым срезом заголовка TTF не
достать. Нужен `libeot` (`eot2ttf`, LGPL) либо резолв семейства по имени из
каталога открытых шрифтов (`Play` — SIL OFL, есть в Google Fonts).

В системе сейчас стоит 59 шрифтов, `Play` среди них нет. Проверено на живом
рендере: подставляется DejaVu/Liberation — и PDF, и PNG, и любое измерение
текста по метрикам уезжают. Значит шрифтовой тракт — не мелочь, а отдельная
фаза с явным журналом подстановок в манифесте прогона и в аудите.

## 3. Проверенные на машине технические решения

| вопрос | что проверено | результат |
|---|---|---|
| нативные графики | `python-pptx add_chart(COLUMN_CLUSTERED)` + `add_table` → LibreOffice → PDF → PNG | **работает**, кириллица в категориях и легенде корректна, конвертация 2 с |
| pptx→pdf | `soffice --headless --convert-to pdf` на колодах 54/55/29 слайдов | 19 с / 16 с / ~15 с; на сгенерированной колоде из 12 слайдов — **2–4 с** |
| pdf→png | `pdftoppm -png -r 60` | 138 страниц за секунды |
| **шаблон как донор** | открыть vk_workspace, снять все слайды, добавить 12 новых на layout шаблона, сохранить | **работает**: открытие 0.1 с, сборка 0.01 с, сохранение 0.31 с, итог 9.2 МБ |
| наследование стиля | текст в `TITLE`-плейсхолдер нового слайда | **наследуется корректно** — белая брендовая гарнитура и кегль подтянулись с layout'а |
| свободный текстбокс | `add_textbox` на тёмном layout'е | **чёрным по чёрному и под декором** → свободные боксы обязаны получать цвет, гарнитуру, кегль и z-order из токенов, а фон под боксом надо знать заранее |
| измерение текста | `fontTools` `hmtx`/`cmap`/`unitsPerEm` | суммирование advance-width даёт ширину строки; кернинг и шейпинг игнорируются → ошибка ~2–3 %, закладываем запас |

Две ловушки, найденные на живом прогоне (сэкономят день на реализации):

1. Снять слайды простым `sldIdLst.remove(...)` **нельзя** — части остаются в
   пакете, `zipfile` при сохранении пишет дубликаты имён и файл бьётся.
   Правильно: `prs.part.drop_rel(sldId.rId)` **и** `sldIdLst.remove(sldId)`.
   Это же уносит media удалённых слайдов: 13.4 МБ → 9.2 МБ.
2. В образе по умолчанию стоит только `libreoffice-core`; **`libreoffice-impress`
   отсутствует**, и `soffice` на .pptx молча отвечает `source file could not be
   loaded`. В Dockerfile нужны `libreoffice-impress` и `poppler-utils` явно.

## 4. Готовые решения: что берём, что не берём

| нужда | взятое решение | почему не альтернатива |
|---|---|---|
| разбор и запись OOXML | `python-pptx` + `lxml` для мест, где API не хватает (группы, темы, встроенные шрифты) | писать свой парсер OOXML — недели; `python-pptx` покрывает 80 %, `lxml` добивает остаток |
| нативные графики | `python-pptx` `add_chart` (реальный `c:chart` part) | рисовать график фигурами — не «нативный chart-объект» по букве ТЗ; хотя сами шаблоны делают именно так |
| нативные таблицы | `python-pptx` `add_table` | — |
| SmartArt-подобные схемы | **сборка из нативных фигур + `cxnSp`-коннекторов в группе** | `dgm:` требует четыре согласованных part'а (`data`/`layout`/`quickStyle`/`colors`) плюс fallback-drawing, python-pptx не умеет, LibreOffice поддерживает частично, а **сам vk_education рисует свои схемы ровно фигурами и коннекторами** (слайд 13) — делаем как дизайнер шаблона |
| pptx→pdf | LibreOffice headless | единственный вменяемый вариант; проверен |
| pdf→png | poppler `pdftoppm` | быстрее и предсказуемее, чем рендер через браузер |
| измерение текста | `fontTools` (метрики) + `Pillow` для проверки | не полагаться на autofit PowerPoint — ТЗ прямо запрещает |
| встроенные шрифты | `libeot`/`eot2ttf` + каталог открытых шрифтов как fallback | распаковка MTX руками бессмысленна |
| структурированный ответ LLM | Pydantic + JSON-схема в запросе + ограниченный repair-loop | регулярки по свободному тексту запрещены п.7 |
| HTML-экспорт | абсолютно спозиционированные `div` из SlideIR | тот же источник истины, что и .pptx — без второй вёрстки |

Отдельно рассмотрены и **отклонены** как основа: `Marp`/`reveal.js`
(markdown→слайды, чужой шаблон не воспроизводят), `pptxgenjs` (JS, генерирует
колоду с нуля, не умеет донорский шаблон), `Quarto`/`python-pptx-templater`
(работают по своим шаблонам с именованными плейсхолдерами — у нас их нет).

## 5. Рекомендация

**Лучший подход — «шаблон-донор + библиотека паттернов» (Template-as-donor +
Pattern Library).**

Шаблон открывается как *донорский документ*. Из него добываются два разных вида
знания:

1. **Токены и правила** — палитра, гарнитуры, типографическая шкала, поля и
   сетка, повторяющиеся элементы. Считаются **статистикой фактического
   употребления**, а не чтением темы (обоснование — §2.2).
2. **Паттерны композиции** — каждый слайд-пример разбирается в
   `Pattern { layout_ref, декор, slots[] (роль, bbox, стиль, подсказка-заглушка),
   repeater{item, ось, шаг, зазор, min..max}, свободная область,
   семантический класс }` (обоснование — §2.3–2.5).

Генерация идёт так: `DeckPlan` (что сказать) → подбор паттерна под блочную
сигнатуру слайда → **клонирование поддерева фигур паттерна из донорского
слайда** с заменой текста и данных → нативные `c:chart`/`a:tbl` там, где нужны
данные. Результат выглядит как шаблон, потому что это **и есть** фигуры
шаблона, а не их пересказ.

**Почему именно так:**

- Это единственный вариант, устойчивый к неизвестному шаблону. Ни одного
  условия по имени, координате или цвету: всё, чем оперирует пайплайн, извлечено
  из файла. Проверка обобщаемости — синтетические holdout-шаблоны, намеренно
  ломающие каждое допущение (см. Q4).
- Собирать фигуры с нуля на layout'ах шаблона (очевидная альтернатива) теряет
  ровно то, за что ставят оценку: градиентные карточки, иконочные чипы,
  декоративные паттерны. На vk_workspace, где у layout'ов нет ни одного
  контентного плейсхолдера, эта альтернатива вырождается в «свой дизайн поверх
  чужого фона» — проверено рендером в §3.
- Клонирование поддерева решает и SmartArt, и пиктограммы, и «фирменный» вид
  графиков без единой строчки под конкретный бренд.

Три варианта вёрстки при этом — **не три пайплайна, а один параметр**:
`LayoutStrategy{density, pattern_preference, data_viz_mode, grouping}`, три
именованных пресета. Ось различий и обоснование — в `ARCHITECTURE.md`.

Полная цепочка слоёв (совпадает с гипотезой ТЗ, уточнены только границы):

```
template.pptx ─►[1 Parse]─► TemplateSpec (токены + layouts + patterns + шрифты + декор)
brief+content ─►[2 Plan ]─► DeckPlan   (слайды: намерение, заголовок-вывод, блоки, данные, источники)
Spec+Plan+strategy ─►[3 Layout]─► SlideIR (абсолютные боксы, стили из токенов, ссылка на донора)
SlideIR ─►[4 Render]─► .pptx ─► .pdf ─► .png ; .html
SlideIR+.pptx+.png ─►[5 Audit]─► Issues[] ─► UI ─► выбранные ─►[Fix]─► 3→4→5
```

`SlideIR` хранит не только геометрию, но и **ссылку на донорскую фигуру**
(`provenance`). Это то, что позволяет рендереру клонировать, а аудиту —
объяснить находку («кегль 11 pt не из шкалы шаблона {9,12,14,16,20}»).
