# Модели

ТЗ ограничивает выбор жёстко (п. 3, критерий A20): только открытые веса,
лицензия Apache 2.0 или MIT, LLM и VLM не больше 35B, text-to-image не больше
20B. Llama и Gemma не подходят по лицензии — у обеих собственные условия, а не
Apache/MIT.

## Что используется

| роль | модель | размер | лицензия | где задаётся |
|---|---|---|---|---|
| текстовая (план, переписывание) | `Qwen/Qwen3.6-27B` | 27B | Apache 2.0 | `LLM_MODEL` |
| со зрением (контекстный аудит) | `Qwen/Qwen2.5-VL-32B-Instruct` | 32B | Apache 2.0 | `VLM_MODEL` |
| text-to-image | не используется | — | — | `T2I_MODEL`, выключено |

Обе укладываются в 35B с запасом. Семейство Qwen выбрано ещё и потому, что
модели этого размера доступны и у публичных провайдеров, и для собственного
инференса — переезд не меняет код.

**Проверяйте лицензию по карточке модели у провайдера перед сдачей.** Здесь
она указана по условиям, на которых семейство опубликовано; провайдер может
раздавать модель на своих условиях, и это его карточка, а не наша таблица.

## Где они крутятся

Разработка — SiliconFlow (OpenAI-совместимый endpoint, домен `.com`).
Финал — инференс VK. Переезд стоит двух строк в `.env`: `LLM_BASE_URL` и
`LLM_MODEL`; код о провайдере не знает ничего, кроме того, что он
OpenAI-совместим.

Text-to-image заложен интерфейсом (`image_provider` в конфиге) и выключен:
задача со звёздочкой, к основному сценарию отношения не имеет.

## Требования к endpoint'у

* OpenAI-совместимый `/v1/chat/completions`;
* у модели со зрением — приём картинок в сообщении (`image_url` с data-URI);
* желательно `/v1/models` для проверки ключа (`deckwright probe` показывает
  список; без него проба работает, но не скажет, есть ли модель).

Параметр, который endpoint не принял, клиент отбрасывает по ответу 400,
повторяет запрос один раз и запоминает это для endpoint'а — прогон не падает,
а факт уходит в манифест (`dropped_params`). Так ведут себя `enable_thinking`
и `reasoning_effort`: они поддерживаются не везде.

## Параметры по шагам

Задаются в `configs/config.yaml`, в разделах `llm.steps` и `vlm.steps`. Имена
шагов — те, которыми код зовёт модель (`llm/base.py: STEPS`): `plan_deck`,
`shorten_text`, `audit_slide`, `audit_deck`. Конфиг с незнакомым именем шага
**не загрузится**: параметры под несуществующим именем не применяются молча, и
это уже стоило нам разбирательства «почему настройка не действует».

Режим рассуждений по умолчанию выключен: блок `<think>` в ответе — это лишние
токены и лишние секунды, а ответ должен быть чистым JSON по схеме. Клиент
снимает такие блоки, если они всё-таки пришли, и считает их в манифесте.

## Замеры на живой модели

`Qwen/Qwen3.6-27B`, SiliconFlow, GitHub Actions (прогоны #6 и #7):

| что | значение |
|---|---|
| планирование колоды | 34 с на вызов (медиана), ≈46 выходных токенов в секунду |
| вопрос аудита по картинке слайда | 15.9 с (медиана), 1469 входных токенов |
| цена картинки при 96 dpi | 882 входных токена (замер разностью запросов) |
| проход аудита по тексту колоды | 12.2 с, раз на колоду |
| формат ответа | 20 из 20 ожидаемых, повторов 0, блоков `<think>` 0, 429 — ноль |
| стоимость пробы (11 вызовов) | $0.019 |

Цены провайдера лежат в `config.yaml` (`price_per_1m_input`,
`price_per_1m_output`), и прогон считает стоимость сам — она идёт в манифест.

**Чувствительность важнее скорости.** На заведомо испорченной колоде модель
назвала три дефекта из четырёх; переполнение рамки пропустила. Подробности и
что с этим делать — в [`AUDIT.md`](AUDIT.md).

### Переписывание текста: замер и что он показал

Прогон #8, та же модель, находка «текст не помещается» на шаблоне
`data/holdout`:

| что | значение |
|---|---|
| время | 25.8 с на две попытки |
| вызовов | 2, повторов 0, блоков `<think>` 0, 429 — ноль |
| токенов | вход 1329, выход 218 |
| стоимость | $0.0011 |

**Модель отработала образцово.** Заголовок 58 → 28 символов, пункты 69/39/44/32
→ 32/25/28/25, всё в бюджете шаблона, новых чисел нет, формат ответа
безупречный.

**И находка не ушла.** Потому что в рамку помещается **две строки**, а абзацев
было пять: сокращать длину строк было бессмысленно с самого начала. Модель не
могла этого знать — ей передавали бюджет шаблона («пункт не длиннее 76
символов»), а не ёмкость этой рамки.

Исправлено: фиттер меряет ёмкость рамки и пишет её в представление, находка
несёт число («помещается 2 строк, занято 5»), промпт переписывания получает
его как главное ограничение, а ответ, который в рамку не влезет, отклоняется
с точной причиной. После этого находка уходит.

Урок общий: **совет без числа не выполняется даже безупречной моделью.**

### Настоящий шаблон датасета: прогоны #9–#11

`data/templates/vk_tech.pptx`, та же модель. Бюджет длины шаблона — заголовок
34 символа, пункт 34, до 6 пунктов (шрифт шаблона Play).

| что | прогон | значение |
|---|---|---|
| планирование, три вызова | #9 | 47.5 / 51.1 / 53.9 с, 39–45 ток/с, повторов 0, 429 — ноль |
| стоимость вызова планировщика | #9 | $0.0076 |
| планирование в сквозном прогоне | #9 | **194.9 с** — см. ниже |
| вопрос по картинке слайда | #10 | 9.9–13.8 с, медиана 13.0 (последовательно) |
| цена картинки при 96 dpi | #10 | 512 входных токенов (слайд 16:9 меньше holdout'а) |
| проход по тексту колоды | #10 | 11.5 с |
| испорченная колода | #10 | поймано 3 из 4, переполнение снова пропущено |
| переписывание по находке | #11 | 3.9 с, 1 вызов, $0.0004 |

**Живой план тоже переполняет рамки — гипотеза «это фикстура» верна лишь
наполовину.** Модель уложилась в бюджет шаблона, и всё равно на пяти слайдах
из десяти текст не помещается: «помещается 2 строк, занято 6», «1 — 15»,
«4 — 5», «3 — 11», «1 — 12». Бюджет один на шаблон («до 6 пунктов»), а
рамки выбранных композиций вмещают от одной до четырёх строк. Следующий шаг
— бюджет по композиции, а не по шаблону: планировщик должен знать, сколько
строк у слайда данного намерения.

**Детерминированная проверка чисел поймала ошибку модели.** Слайд 8: модель
написала выведенное число «21», а формула, которую она же указала,
`(f1 + f3) / 2`, даёт 25.5. Это единственная находка уровня ERROR, и именно
та, ради которой происхождение чисел проверяется кодом, а не моделью.

**Переписывание отклонено — и правильно.** В рамку помещается две строки, а
в повестке четыре пункта. Модель вернула тот же текст; ограничитель ёмкости
не принял его («5 строк при ёмкости рамки 2»), и находка осталась с
причиной, а не исчезла молча. Уложить четыре пункта в две строки
переписыванием нельзя — нужна другая композиция, это тот же дефект бюджета.

**194.9 с на планирование вместо 50.** В пробе тот же вызов занимает
47.5–53.9 с. Повторов по схеме и 429 в пробе нет, а сквозной прогон этих
счётчиков тогда не печатал. Вероятнее всего — таймаут 120 с и повтор внутри
SDK, невидимый нашим счётчикам. Теперь `run` печатает вызовы, повторы, 429
и самый долгий вызов (`slowest_call_seconds`, есть и в манифесте): вызов
дольше таймаута и есть такой повтор. Это главный риск бюджета A18 — один
такой вызов съедает две трети пяти минут.

## Работа без модели

Прогон без ключа обязан работать, иначе интерфейс нечем показать, а CI нечем
проверить. `--recorded` подставляет записанные ответы из
`tests/fixtures/recorded/`; в этом режиме контекстные проверки аудита честно
попадают в `skipped_checks` с причиной «модель недоступна», а не выдают пустой
список находок за «всё хорошо».
